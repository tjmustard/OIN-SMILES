# Process Document: MetalloGen 3D Generator & MACE GPU Acceleration

**Generated:** 2026-07-05T15:15:05-07:00
**Session Focus:** Implementing the MetalloGen 3D generator backend, adding MACE-based MLIP optimization, and resolving GPU (GTX 1080/sm_61) hardware incompatibilities with graceful CPU/FF fallbacks.

## Problem Statement

OIN-SMILES needed the ability to generate reliable 3D structures from OIN strings using advanced Machine Learning Interatomic Potentials (MLIPs), specifically MACE (MACE-OMol25 and mace-omol-0). Furthermore, running these models locally required GPU acceleration, but the target environment contained an older GTX 1080 (Pascal `sm_61` architecture) which is unsupported by modern PyTorch binaries out of the box.

## Starting State

The codebase possessed a legacy Force Field-based embedding pipeline (via `scine-molassembler`). A new `MetalloGen` 3D generation module was recently scaffolded into `src/oinsmiles/generator3d/` with xTB optimizer stubs. MACE support and dynamic hardware compatibility/fallback cascades were entirely absent.

## Approach & Methodology

The approach was iterative execution and debugging:
1. **Integration**: Plumbed the MACE calculators into the `ASEOptimizer` class.
2. **Strictness Enforcement**: Removed silent failures across the pipeline to ensure errors were initially caught loudly.
3. **Environment Configuration**: Integrated `python-dotenv` for local model paths and implemented command-line parameter propagation (`--ensemble-size`, `--optimizer`).
4. **Hardware Remediation**: Diagnosed PyTorch's silent failure on `sm_61` and orchestrated a downgraded dependency lock to a specific PyTorch CUDA 11.8 wheel.
5. **Fallback Cascade**: Implemented a robust three-tier (GPU → CPU → FF) graceful execution fallback within the MLIP optimizer to catch runtime CUDA errors (like OOM or unsupported kernels).

## Steps Taken

1. **Parameter Propagation**: Updated `tests/run_verification.sh` and other shell scripts (`run_integration.sh`, `run_verification_ALL.sh`, `run_verification_fast.sh`) to actively parse and forward `--optimizer`, `--ff-preset`, and `--ensemble-size` flags to the underlying python tests.
2. **Diagnosing GPU Failure**: Attempted to execute MACE on the GPU. PyTorch threw `cudaErrorNoKernelImageForDevice` because versions 2.4+ dropped support for Pascal (`sm_61`).
3. **Dependency Pinning**: Forced `uv` to use `torch==2.3.1` with the `cu118` index by using `uv add torch==2.3.1 --index https://download.pytorch.org/whl/cu118 --index-strategy unsafe-best-match`. This permanently modified `pyproject.toml` and updated the `uv.lock` file to pull the correct CUDA 11.8 binaries.
4. **Verification**: Executed a single example using `verify_roundtrip.py` with the MACE optimizer. The CUDA `matmul` smoke test successfully executed, and MACE ran natively on the GTX 1080 GPU.
5. **Warning Suppression**: MACE triggered a `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD` PyTorch warning on CPU initialization. Added a targeted `warnings.catch_warnings()` context manager in `ml_optimizer.py` to suppress this specific log spam.
6. **Graceful Fallback Logic**: Refactored `ml_optimizer.py` to iterate through available devices `["cuda", "cpu"]`. If `opt.run()` encounters a CUDA error (like OOM or architecture mismatch), it resets the atomic positions and retries natively on CPU. If the CPU MLIP optimization fails, it catches the exception and returns `False`, instructing the `OIN3DGenerator` to gracefully retain the original Force Field embedded coordinates.
7. **Stress Testing**: Wrote a custom script `run_tmqm_stress_test.py` to test the fallback logic on massive organometallic complexes from the `tmQM` dataset. The test was canceled manually due to excessive time spent in RDKit's UFF embedding prior to MLIP execution, but the fallback code logic was verified as structurally sound.

## Key Decisions & Rationale

| Decision | Alternatives Considered | Reason Chosen |
|---|---|---|
| Use `torch.matmul` for GPU capability check | `torch.cuda.is_available()` alone | `torch.cuda.is_available()` returns `True` for unsupported architectures (e.g., `sm_61` on PyTorch 2.5), causing a crash later during the MLIP calculation. A dummy `matmul` forces a kernel launch, accurately detecting hardware incompatibility. |
| Modify `pyproject.toml` for PyTorch 2.3.1 | Compile PyTorch from source, or use `uv run --with` | Compiling is too slow. `uv run` implicitly syncs back to the lockfile's default PyPI torch package (2.5+) overriding the manual `uv pip install`. Adding the `cu118` index to `pyproject.toml` permanently resolved the dependency for the environment. |
| GPU → CPU → FF Fallback Cascade | Fail completely if GPU OOMs | MetalloGen runs in automated pipelines over large conformer pools. It's better to get a valid CPU optimization, or a valid FF geometry, than to crash the entire batch job due to a single conformer memory spike. |

## Patterns & Lessons

- **`uv run` Dependency Isolation**: `uv run` strictly enforces the environment matched by `uv.lock`. Manual injections via `uv pip install` are wiped implicitly. When managing deep-learning dependencies (like `torch` indices), always use `uv add` with `--index` and `--index-strategy` so it records in `pyproject.toml`.
- **PyTorch Hardware Depreciation**: PyTorch 2.4/2.5 silently drops support for Pascal (`sm_60`, `sm_61`) architectures, even in the `cu118` wheels. `torch.cuda.is_available()` will lie. You must force a compute kernel (`matmul`) in a try/except block to truly verify GPU compatibility.
