## Results & Outcomes

TASK-20 is DONE with a conclusive, reproducible finding: **the P/N-stereocenter gap is at XYZ→OIN encoding, not OIN→XYZ generation — and the information is recoverable, not lost.** Any P/N atom that coordinates the metal directly is unconditionally stripped of its chiral tag by `ChiralityRecoveryUtility.recover()`'s Zone-A rule (`core/chirality.py:155-158`), because OIN's fragment SMILES structurally excludes the metal, leaving such an atom with only 3 fragment-local neighbors — always below the 4-neighbor threshold the code checks, and the strip happens *before* the branch that would consult `_OIN_CIPCode`. Critically, `_OIN_CIPCode` is still computed by `CIPAssigner` from the intact pre-fragmentation 3D structure (metal present) and is still attached to the atom when the strip runs — the strip simply discards a value that was already correctly derived. `PseudoAtomStrategy`, the mechanism apparently purpose-built to backfill a wildcard 4th substituent for exactly this case, is dead code with zero call sites. This means Phase 2 of the stereo roadmap ("verify/enforce ligand `@/@@` through ETKDG") has nothing to test as originally scoped — no `@`/`@@` reaches generation — and folds into Phase 4 ("Zone-A P/N stereo + builder decision"). Phase 4 is a FORMAT/ENCODING decision (how should OIN represent a metal-bound stereocenter — revive the wildcard-metal pseudo-atom, a lone-pair `[P@]` 3-neighbour SMILES convention, or a separate slot-ordering-style annotation?), not a generation-side code fix, and touches `core/chirality.py` (the encode side) rather than just the builder — so it should start with a design consult rather than going straight into `/hyper-architect`. Test suite remains green throughout: `tests/unit` → 65 tests, `OK (skipped=1, expected failures=3)`.

## Patterns & Lessons

- When a diagnostic task's own sanity-check assertion fails before its main assertion, that is itself a legitimate and often more valuable diagnostic result than the main assertion — don't treat it as a test-writing error; investigate and report the earlier failure point precisely, since it usually points at a different (and sometimes more fundamental) root cause than the one the task assumed.
- Before writing tests that encode assumptions about output format, run the code under test directly first (`XYZToSMILES().convert(...)`) and inspect the raw output — this session's finding (no `@` at all, not merely a lossy round-trip) would have been missed if the tests had been written from the spec alone without an empirical check first.
- Grepping for zero call-sites is a fast, reliable way to confirm a class/function is dead code before relying on it in a root-cause narrative (used here to confirm `PseudoAtomStrategy` is unwired).
- This project maintains dual fixture directories (`tests/fixtures/` for unittest-driven diagnostics, `tests/integration/` for capitalized-name integration/verification scripts) — when adding a new complex fixture, check whether both are expected and mirror existing naming pairs (e.g. `PdCl2-RR-BDPP.xyz` appears in both) rather than picking one arbitrarily.
- The task's own outcome protocol (from TASK-10, reused by TASK-20) — "if a test unexpectedly passes, convert to hard assert; if it fails, record the finding and defer the fix to its own HACF-chain task" — is a reusable pattern worth keeping for future stereo-roadmap diagnostic tasks (Phase 3, Phase 4).
