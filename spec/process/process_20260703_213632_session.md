## Patterns & Lessons

- A MiniPRD's own prose description of a fixture's properties ("compatible-bite") can be wrong
  even in a Red-Team-reviewed, resolved, compiled document — always verify empirically
  (`XYZToSMILES().convert()`, or a direct probe of the relevant internal function) before
  building tests or fixtures around it.
- A single-vector rigid-body alignment (`Rotation.align_vectors` with one source/target pair)
  always leaves one rotational degree of freedom undetermined. Any new orientation logic built
  on this pattern needs an explicit secondary objective (clash avoidance, here) for that
  residual DOF, or it will pick an arbitrary — and sometimes badly clashing — angle.
- Per-fragment placement loops that build up `forbidden_positions` incrementally are inherently
  order-dependent: a fragment placed early cannot avoid clashing with one placed later. The fix
  is not to reorder fragments (fragile, order may carry other meaning) but to add a
  post-placement verification pass, once every fragment has been placed at least once, reusing
  whatever retry/re-embed infrastructure already exists for a different purpose (here, stereo
  verification).
- `Chem.MolToSmiles` canonicalisation silently breaks any assumption that atom indices computed
  before it still apply after re-parsing the resulting string — this is a recurring trap
  (`_build_connected_smiles` does this) and worth checking explicitly whenever atom-index
  bookkeeping needs to survive a SMILES round-trip.
- When a user's mid-session request conflicts with an already-resolved, Red-Team-reviewed
  constraint in the active spec (here: "invest in general clash avoidance" vs. "every existing
  golden must stay byte-identical"), the right move is to try it, observe the concrete break,
  revert, and report the conflict with evidence — not to silently comply or silently refuse.
